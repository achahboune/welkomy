# Welkomy API

Cloudflare Worker API for the Welkomy host dashboard and public guest guides.

## Stack

- Hono HTTP API
- Better Auth email/password authentication and cookie sessions
- Cloudflare D1 for users, sessions, accounts, verifications, and properties
- React/Vite frontend in `apps/web`

## Cloudflare resources

The Worker is configured in `wrangler.toml` to use the D1 database:

- Name: `welkomy-db`
- Binding: `DB`
- Migration directory: `migrations`

The initial migration creates both Better Auth's core tables and the `properties` table. It is a single migration; do not run a separate Better Auth migration on top of it.

## Local development (Windows CMD)

Run commands from the repository root.

1. Create `apps/api/.dev.vars` with a random secret of at least 32 characters and local URLs:

```dotenv
BETTER_AUTH_SECRET=replace-with-a-random-secret-at-least-32-characters
BETTER_AUTH_URL=http://localhost:8787
APP_ORIGIN=http://localhost:5173
ENVIRONMENT=development
```

Do not commit `.dev.vars`.

2. Apply the migration to the local Wrangler D1 database only:

```cmd
npx wrangler d1 migrations apply welkomy-db --local
```

This does not modify the remote Cloudflare database.

3. Open two CMD windows in the repository root:

Terminal 1 (API):

```cmd
npm run dev --workspace @welkomy/api
```

Terminal 2 (frontend):

```cmd
npm run dev --workspace @welkomy/web
```

Open the Vite URL shown in Terminal 2 (normally `http://localhost:5173`).

## Production configuration

Before deploying, configure these Worker variables/secrets in the Cloudflare dashboard:

- Secret `BETTER_AUTH_SECRET`: unique random value, at least 32 characters.
- `BETTER_AUTH_URL`: exact public Worker API origin, for example `https://api.example.com`.
- `APP_ORIGIN`: exact public frontend origin, for example `https://app.example.com`.
- `ENVIRONMENT`: `production`.

Use HTTPS and preferably put the frontend and API on subdomains of the same custom domain so browser cookie policies do not block the session. Do not leave localhost URLs in production.

Only after checking the Cloudflare account and the D1 database ID, apply the migration remotely:

```cmd
npx wrangler d1 migrations apply welkomy-db --remote
```

Then deploy the Worker:

```cmd
npx wrangler deploy
```

Deploy the frontend separately to Cloudflare Pages with the correct API URL if it is not served through the same origin.

## API routes

- `GET /api/health` — public health check
- `/api/auth/*` — Better Auth email/password endpoints
- `GET /api/properties` — list the signed-in user's properties
- `POST /api/properties` — create a draft property
- `PUT /api/properties/:id` — update an owned property
- `DELETE /api/properties/:id` — delete an owned property
- `GET /api/properties/:id/guide` — read an owned guide
- `PUT /api/properties/:id/guide` — save an owned guide
- `POST /api/properties/:id/publish` — publish an owned guide
- `POST /api/properties/:id/unpublish` — unpublish an owned guide
- `GET /api/public/guides/:slug` — read a published guide without signing in

Every private property query is scoped to the authenticated user's ID. The API never accepts an owner ID from the client.

## Current MVP limits

- Email/password only; email verification and password reset emails are not configured.
- Guest guide content currently supports Wi-Fi, check-in, check-out, access, emergency contact, and notes.
- The QR code is generated by a free third-party QR endpoint.
- Automated end-to-end tests and production deployment still need to be completed.
